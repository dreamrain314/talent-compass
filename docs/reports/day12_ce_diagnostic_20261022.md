## 三、问题 3 输入路径检查（代码实锤，按排查清单逐项）

1. **query/document 编码方式不符合 checkpoint 用法**（实锤）：`utils/label_embedding.py:_embed` 对 query 与 chunk 同走 fastembed `model.embed()`，query 侧**未加 bge 检索指令前缀**（bge-small-zh-v1.5 官方推荐 query 加指令、passage 不加；fastembed 有 `query_embed`/`passage_embed` 分工接口未使用）。
2. **CE 入场券被 T0 支配**（实锤，比预想严重）：`rank_candidates` L421-422 短名单 = **按含 T0×50 的 prelim 总分**取 Top-10。B06 金标 bi 第 9 但 T0 低 → prelim 跌出前 10 → CE 未见金标（fused_t1=0.4814=bi 原值，未被校准）→ 融合第 44。**「CE 有没有纠错机会」的闸门由被宣判缺乏鲁棒性的 T0 字面层把守**——这正是 pooled CI 双 FAIL 的结构性成因之一。
3. **压缩/裁剪链**（实锤，三段）：bi_raw → floor 0.30 截断归零再归一化（score_t1_bi）；CE logit → sigmoid → 按 queries 求 mean（calibrate_t1_with_ce，多条强证据被均值稀释）；blend 0.5 线性混合。CE 全员动态范围仅 ~0.03–0.12（均值 0.51 起），三段压缩的叠加产物。
4. **blend 0.5 量纲**（实锤）：短名单内 ce−bi 差 −0.008 ~ +0.087 随机正负，两通道均值各自漂移（bi_mean 0.42–0.52 / ce_mean 0.51–0.56 且不同岗错位），各占一半无可解释依据。
5. **截断风险排除**（阴性结果也有价值）：656 chunks，长度 mean 55 / p95 150 / max 150 字符，无 >400 字 chunk；chunk/员工 10–17 条。长履历截断、证据落尾这两条**不成立**，从嫌疑清单划掉。
6. pooling：bi 人级 = 每 query max-pool chunk → queries 均匀 mean——只记每 query 最强一条证据，其余丢弃；与要求级覆盖的思路天然不兼容（一个员工在多个要求上各有中强证据，会被"每要求只留一条再平均"摊平）。

## 四、结论（对预注册的回填）

1. **不训练的假设被数据支持**：CE 排名差的主因不在模型容量，在 ①候选准入被 T0 把持 ②top1-chunk×mean 的信息稀释 ③sigmoid+blend 的压缩链。三条都是结构问题。
2. **「改结构」方向获第一轮独立证据**：要求—证据片段化直接针对 ②③；取消 T0 主导的 Top-10 截断直接针对 ①。
3. **下一步按排期进 Day 3-5**：要求—证据切片 + 关系分类 + 要求级聚合（预注册 §二），CE 全量候选评分作为诊断口径保留。
4. **遗留人工项（问题 1）**：JD—证据可证性复核表模板随本报告产出（`day12_verifiability_review_template.md`），由用户不看模型分数人工复核后回填。
