## 🔴 严重 Bug

### Bug #9 (F-101): `_execute_with_timeout` 重试时旧线程未真正终止

- **文件:** `orchestrator/pipeline.py:123-143`
- **严重程度:** 🔴 严重
- **代码:**

```python
for attempt in (1, 2):
    cancel_event = threading.Event()
    ctx = {**context, "cancel_event": cancel_event}
    executor = concurrent.futures.ThreadPoolExecutor(max_workers=1)
    future = executor.submit(agent.run, data, ctx)
    try:
        result = future.result(timeout=timeout)
        executor.shutdown(wait=False)
        return result
    except concurrent.futures.TimeoutError:
        cancel_event.set()
        executor.shutdown(wait=False, cancel_futures=True)
        if attempt == 1:
            continue          # ← 重试，但旧 Agent 线程仍在运行！
```

- **根因:** `shutdown(wait=False, cancel_futures=True)` 只能取消**尚未开始执行**的任务。对于已经在 `agent.run()` 内部执行的线程（若 Agent 调用 LLM 卡在 `client.chat.completions.create()` 的阻塞 I/O 中），Python 线程模型**不支持强制终止**。旧线程变成事实上的守护泄漏——占用内存和网络连接，直到进程退出。
- **`cancel_event` 的致命时间差:** Agent 在 `execute()` 中检查 `cancel_event.is_set()`，但 `cancel_event.set()` 只有在**超时发生之后**才被调用。在超时之前的 120 秒内，Agent 全程不响应取消信号。这是"先超时再通知"而非"先通知再超时"的倒置设计。
- **影响:** 若 Agent 持有 LLM 连接阻塞在 socket read，连接永不释放。重试的第二次 Agent 也大概率在同一网络问题上超时。最终 Pipeline 返回 degraded，但 2 个僵尸线程持续运行。
- **修复建议:**

```python
# 方案 A（推荐）：超时先行通知，给 Agent 优雅退出的窗口
cancel_event = threading.Event()
# 在超时前 5 秒设置取消信号，给 Agent 反应时间
timer = threading.Timer(timeout - 5, cancel_event.set)
timer.start()
try:
    result = future.result(timeout=timeout)
finally:
    timer.cancel()
    executor.shutdown(wait=False, cancel_futures=True)
# Agent 的 execute() 应在每次 LLM 调用前检查 cancel_event

# 方案 B（彻底）：用 multiprocessing.Process 替代线程
# Process 可以真正被 SIGTERM/SIGKILL 终止，不存在僵尸泄漏
```

### Bug #10 (F-102): `current_data = step_result.get("data", {}) or {}` 静默丢弃 falsy 数据

- **文件:** `orchestrator/pipeline.py:76`
- **严重程度:** 🔴 严重
- **代码:**

```python
current_data = step_result.get("data", {}) or {}
```

- **数学验证:**

| `step_result["data"]` 值 | `step_result.get("data", {})` | `... or {}` | 最终值 | 是否被篡改 |
|---|---|---|---|---|
| `None` | `None` (key 存在，值为 None) | `{}` | `{}` | ✅ 合理 |
| `{}` | `{}` | `{}` | `{}` | ✅ 不变 |
| `{"a":1}` | `{"a":1}` | `{"a":1}` | `{"a":1}` | ✅ 不变 |
| `[]` | `[]` | `{}` | **`{}`** | ❌ **空列表被丢弃** |
| `0` | `0` | `{}` | **`{}`** | ❌ **数字0被丢弃** |
| `False` | `False` | `{}` | **`{}`** | ❌ **False被丢弃** |
| `""` | `""` | `{}` | **`{}`** | ❌ **空字符串被丢弃** |

- **根因:** `A or B` 将 A 的 falsy 值（`None, 0, "", [], {}, False`）全部回退到 B。当 `get("data", {})` 返回 `None`（key 存在但值为 None）时回退到 `{}` 是正确的，但 `[]`、`0` 等 valid 空值也被错误地回退。
- **第一轮 Bug #1-#8 教训的再犯:** 这是**第三次**出现"看起来正确但逻辑有缺陷"的模式——视觉 review 极难发现。类似 Bug #1（timeout 假生效）、Bug #2（偏差公式恒等变换）。
- **修复建议:**

```python
val = step_result.get("data")
current_data = {} if val is None else val
```

### Bug #16 (F-108): `_get_client()` 无线程锁保护

- **文件:** `utils/llm_client.py:17-30`
- **严重程度:** 🟡 重要
- **代码:**

```python
_client: OpenAI | None = None
_last_api_key: str | None = None

def _get_client() -> OpenAI:
    global _client, _last_api_key
    current_key = os.getenv("DEEPSEEK_API_KEY", DEEPSEEK_API_KEY)
    if _client is None or _last_api_key != current_key:  # ← 无锁检查
        _client = OpenAI(api_key=current_key, ...)        # ← 无锁写入
        _last_api_key = current_key                       # ← 无锁写入
    return _client
```

- **根因:** PipelineRunner 使用 `ThreadPoolExecutor`。两个线程同时进入 `if _client is None` 分支 → 各自创建 client → 先创建的 client 被丢弃 → 连接泄漏。
- **影响:** 概率性触发（取决于线程调度时序），在 Demo 阶段低并发下几乎不可见，但生产阶段可能累积大量废弃连接。
- **修复建议:**

```python
import threading
_lock = threading.Lock()

def _get_client() -> OpenAI:
    global _client, _last_api_key
    current_key = os.getenv("DEEPSEEK_API_KEY", DEEPSEEK_API_KEY)
    with _lock:
        if _client is None or _last_api_key != current_key:
            _client = OpenAI(api_key=current_key, base_url=DEEPSEEK_BASE_URL)
            _last_api_key = current_key
    return _client
```

- **代码:** `ext=set(list(anom)[:2])` —— set 转 list 依赖 hash 种子，不同 Python 运行可能将不同员工分配为"极端评价者"vs"偏差评价者"。
- **影响:** 种子 42 在 CPython 3.10/3.11/3.12 之间 set 迭代顺序可能不同，导致数据不可复现。
- **修复:** `anom_list = sorted(anom)` 或 `anom_list = random.sample(eids, 4)` (已经是采样的，再用 sorted)。

### Bug #25 (F-117): `call_llm_json()` 中 `jsonschema` 未安装时静默跳过校验

- **文件:** `utils/llm_client.py:107-113`
- **影响:** 在未安装 jsonschema 的环境（如 Docker 镜像），`json_schema` 参数被静默忽略，Agent③ 的结构化输出校验完全失效，无异味。
- **修复:** ImportError 时至少 `log.warning` 加上提示信息（当前已有），但更好的做法是在 `requirements.txt` 中确保 jsonschema 必装（当前已包含 `jsonschema>=4.20.0`，问题不大）。

# 代码生成根本原因分析与预防体系

> **核心问题:** 为什么经过第一轮 8 个 Bug 的修复 + 7 条反模式规则 + CLAUDE.md 编码规范，第二轮仍然发现 17 个 Bug？
>
> **答案:** 因为规则覆盖的是**已发现的模式**（超时、数学变换、默认参数、死代码、单例、数据一致性），但 Bug 的**生成机制**没有得到阻断——AI 生成代码时倾向于（a）防御性代码过度泛化（b）多模块间不交叉校验（c）对"看起来正确"的代码不做自证。

---

## 根因分类

### 根因 A: "防御性代码"本身引入新漏洞（Bug #10, #17, #22）

| Bug | AI 的思维模式 | 为什么规则没挡住 |
|-----|-------------|----------------|
| #10 `or {}` | "step_result 可能不含 data key，我得防御一下" | Rule 5（except 必须有实质差异）只约束 try/except，不约束 `or` 短路 |
| #17 `str(v)` | "直接 json.dumps 可能失败，我先转成 string" | 规则没要求"降级方案必须可逆" |
| #22 双重 sys.path | "在 main.py 加了 path 操作，ui/app.py 作为独立页面也应该加" | 规则没要求"跨文件检查重复逻辑" |

**本质:** AI 对"防御性编程"的理解是机械式的——给每个操作加保护层，但不检查保护层自身的正确性。**任何防御性代码都需要反证其不引入新问题。**

### 根因 B: 跨模块一致性未被检查（Bug #12, #15, #18）

| Bug | 矛盾 | 为什么规则没挡住 |
|-----|------|----------------|
| #12 data_lineage | CLAUDE.md 要求 vs BaseAgent 实现 | Rule 3 只约束"默认参数值"，不约束"metadata 字段完整性" |
| #15 config 矛盾 | config.py 默认值 vs .env 实际值 | 规则针对**代码内部**的默认值，不针对**代码和配置文件之间**的默认值 |
| #18 output_dir | PipelineRunner 硬编码 vs config.py 常量 | 规则没有"禁止重复定义路径"的条目 |

**本质:** AI 在生成模块 A 时不考虑模块 B 的已有定义。每份代码在生成时是**上下文孤岛**——LLM 只看到当前文件、当前函数。

### 根因 C: API 返回值契约未约定（Bug #13, #14）

| Bug | 问题 | 为什么规则没挡住 |
|-----|------|----------------|
| #13 call_llm 返回格式二分 | 成功和失败返回不同的 key | 没有规则约束"公共函数的返回格式必须成功/失败对称" |
| #14 call_llm_json 返回格式三态 | 三种场景三种格式 | 同上 |

**本质:** 两个函数由同一个 agent 在同一轮生成，但 agent 在写 `call_llm_json` 时没有回顾 `call_llm` 的返回格式作为契约基准。**同一模块内函数的 API 契约应该被显式声明和验证。**

### 根因 D: 不可见假设未暴露（Bug #9, #16）

| Bug | 隐藏假设 | 为什么规则没挡住 |
|-----|---------|----------------|
| #9 超时重试 | "Python 线程可以被取消" | Rule 1（超时必须边界测试）已存在，但测试的 `_HangingAgent` **主动检查 cancel_event** 而真实 Agent **阻塞在 I/O 不检查**——测试与真实场景不同构 |
| #16 无线程锁 | "LLM client 只在主线程使用" | Rule 6（单例支持运行时重配置）只约束配置更新，不约束线程安全 |

**本质:** 测试覆盖了"Agent 配合取消"的理想路径，忽略了"Agent 不配合取消"的真实路径。**边界测试必须模拟被测代码的精确失败模式，而非通用延迟。**

## 预防规则升级（v1 → v2）

在第一轮 7 条规则的基础上，新增以下规则。合计 12 条。

### 规则 8（新增）: 防御性代码必须附带反向验证

**对应 Bug:** #10（`or {}` 静默丢弃 falsy）, #17（`str(v)` 破坏结构）

**规则:**
- 任何使用了 `or` 短路、`str()` 强制转换、`try/except` 降级、或默认值回退的代码，必须附带一个**反向验证表**：
  - 列出 5-10 个可能的输入值
  - 标注每个输入经过该防御逻辑后的输出
  - 确认没有任何 valid 输入被错误转换
- 类似 Rule 2 的数学变换验证表，但范围扩展到**所有类型转换防御代码**。

```
示例模板（Bug #10）:
输入值           →  get("data", {})  →  or {}  →  最终值  →  判定
None (key缺失)    →  {}              →  {}     →  {}      →  ✅
None (key存在)    →  None            →  {}     →  {}      →  ✅
{"a": 1}          →  {"a": 1}        →  {"a": 1} → {"a":1} → ✅
[]                →  []              →  {}     →  {}      →  ❌ BUG
0                 →  0               →  {}     →  {}      →  ❌ BUG
```

### 规则 9（新增）: 跨模块常量必须单向引用

**对应 Bug:** #18（output_dir 硬编码）, #22（双重 sys.path）

**规则:**
- 任何被 ≥2 个模块使用的配置值（路径、阈值、超时时间、模型名），只允许在**一个地方定义**（通常是 config.py 或 CLAUDE.md），其他模块必须 import 或引用。
- **禁止**两个模块各自定义相同语义的默认值。
- 代码审查时 grep 相同字符串常量出现 ≥2 次 → 默认视为违规。

### 规则 10（新增）: 公共函数返回格式必须声明对称契约

**对应 Bug:** #13, #14

**规则:**
- 任何被 ≥2 个调用方使用的函数，必须在 docstring 中声明**成功和失败时的完整返回格式**。
- 格式必须对称：成功和失败返回相同的顶层 key 集合，用 `"error": None` vs `"error": "message"` 区分。
- **禁止**成功返回 3 个 key、失败返回 1 个 key 的不对称设计。

```python
# ✅ 对称契约
def call_llm(...) -> dict:
    """
    Returns:
        dict: ALWAYS contains {"content": str|None, "error": str|None,
              "usage": dict, "model": str}
        - Success: error=None, content=str
        - Failure: error=str, content=None
    """
```

### 规则 11（新增）: 边界测试必须模拟精确失败模式

**对应 Bug:** #9（超时测试的 Agent 配合取消 vs 真实 Agent 阻塞 I/O 不配合）

**规则:**
- 为某段代码写边界测试时，必须模拟**该代码在生产环境中的精确失败模式**。
- 例如：测试超时机制 → 用 `socket.socket().connect()` 连一个不存在的地址（真实阻塞 I/O），而非 `time.sleep()`（不阻塞 I/O 的事件循环）。
- 测试不能"模拟一个配合的对手"，必须"模拟一个不配合的真实对手"。

### 规则 12（新增）: Metadata 契约必须在基类中强制

**对应 Bug:** #12（data_lineage 缺失）

**规则:**
- 任何在抽象基类规范中声明的输出字段（如 metadata 的子字段），基类必须**要么自动注入默认值，要么在 `__init_subclass__` 中校验子类是否覆盖**。
- **禁止**纯文档约定的 metadata 字段——文档约定在实现阶段必然遗漏。
