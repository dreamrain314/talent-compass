## 三、Bug 清单（按严重程度排列）

### 🔴 严重 Bug

#### Bug #1: `_execute_with_timeout` 超时机制完全失效

- **文件:** `orchestrator/pipeline.py:103-147`
- **严重程度:** 🔴 严重
- **代码:**

```python
# 第 109-111 行
with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
    future = executor.submit(agent.run, data, context)
    result = future.result(timeout=timeout)
```

- **现象:** 设置 timeout=120s，但如果 Agent 线程卡死，整个 Pipeline 会被永久阻塞
- **根因:** `ThreadPoolExecutor.__exit__` 方法内部调用 `shutdown(wait=True)`。即使用 `future.result(timeout=...)` 抛出了 `TimeoutError`，`with` 语句退出时仍会**等待线程执行完毕才释放**。Python 线程无法被强制终止，超时形同虚设
- **实测验证:**

```
模拟一个 10 秒的任务，timeout=2 秒
→ 实际耗时: 10.0 秒（而非预期的 ~2 秒）
→ BUG 确认
```

- **影响:** 如果 Agent① 调用 LLM 时网络卡死，整个 Pipeline 将无限期等待，Streamlit 界面也会卡死
- **修复建议:**
  - 方案 A：使用 `multiprocessing.Process` 替代线程（可真正 kill）
  - 方案 B：使用 `threading.Event` 作为取消标志，Agent 内部定期检查；超时后设置取消标志并 `future.cancel()`
  - 方案 C：使用 `asyncio.wait_for` + 协程（需改造为异步架构）

#### Bug #2: 360评价的"偏差评价者"公式是恒等变换，偏差数据完全无效

- **文件:** `data/generate_mock_data.py:122`
- **严重程度:** 🔴 严重
- **代码:**

```python
sc = abs(sc-3)+3 if sc>3 else 3-abs(sc-3)
```

- **数学推导:**

| 输入 sc | 计算过程 | 输出 | 是否变化 |
|---------|----------|------|----------|
| 1 | `3 - abs(1-3) = 3 - 2 = 1` | 1 | ❌ 不变 |
| 2 | `3 - abs(2-3) = 3 - 1 = 2` | 2 | ❌ 不变 |
| 3 | `3 - abs(3-3) = 3 - 0 = 3` | 3 | ❌ 不变 |
| 4 | `abs(4-3) + 3 = 1 + 3 = 4` | 4 | ❌ 不变 |
| 5 | `abs(5-3) + 3 = 2 + 3 = 5` | 5 | ❌ 不变 |

- **结论:** 对任意输入，输出恒等于输入。这是一个**数学恒等式**，不会产生任何偏差效果
- **影响:** 需求中要求"设计 3-5 个异常评价者：某评价者打分与其他人明显偏离"——只有"极端评价者"（全 5 分，JZ0023/JZ0079）生效，**偏差评价者完全不存在**。这导致 360 评价数据缺乏真实场景中的噪声特征，后续 Agent① 的异常评价者检测（步骤 1.4）将缺少测试数据
- **实测验证:**

```python
for sc in range(1, 6):
    dev = abs(sc-3)+3 if sc>3 else 3-abs(sc-3)
    print(f"sc={sc} -> dev={dev} (changed: {sc != dev})")
# 输出: 全部 changed: False
```

- **修复建议:**
  ```python
  # 方案：使评分偏离均值（3分），向极端方向移动
  if sc >= 4:
      sc = min(5, sc + 2)   # 本来偏高 → 拉到接近 5
  elif sc <= 2:
      sc = max(1, sc - 2)   # 本来偏低 → 拉到接近 1
  # sc=3 保持不变
  ```

#### Bug #5: `_save_intermediate` 的 try/except 是死代码

- **文件:** `orchestrator/pipeline.py:155-163`
- **严重程度:** 🟡 中等
- **代码:**

```python
try:
    serialized = json.dumps(result, ensure_ascii=False, indent=2, default=str)
except (TypeError, ValueError) as e:
    logger.warning(
        f"JSON serialize partial failure: {e}",
        extra={"trace_id": trace_id, "agent_name": "PipelineRunner"},
    )
    serialized = json.dumps(result, ensure_ascii=False, indent=2, default=str)
    # ^^^ 与 try 块完全相同！如果第一次失败，第二次也会以相同方式失败
```

- **影响:** 异常处理形同虚设。如果存在不可序列化的对象（如 `bytes`、`datetime` 等），第一次 `json.dumps` 失败，第二次也会失败，最终抛出未捕获的异常导致 Pipeline 崩溃
- **修复建议:**
  ```python
  except (TypeError, ValueError) as e:
      logger.warning(...)
      # 降级处理：只保存可序列化的部分
      try:
          serialized = json.dumps(
              {"status": result.get("status"), "error": str(e)},
              ensure_ascii=False, indent=2
          )
      except Exception:
          serialized = '{"error": "serialization failed completely"}'
  ```

#### Bug #6: `_get_client()` 单例缓存导致 API Key 运行时更新无效

- **文件:** `utils/llm_client.py:12-19`
- **严重程度:** 🟡 中等
- **代码:**

```python
_client: OpenAI | None = None

def _get_client() -> OpenAI:
    global _client
    if _client is None:
        _client = OpenAI(api_key=DEEPSEEK_API_KEY, base_url=DEEPSEEK_BASE_URL)
        #                    ^^^^^^^^^^^^^^^^ 只在首次调用时读取
    return _client
```

- **影响:** 用户在 Streamlit 侧边栏输入新的 API Key → `os.environ["DEEPSEEK_API_KEY"] = api_key` → 但 `_client` 在首次调用时已用**旧 Key**（或空 Key）创建，永不再更新。除非用户刷新整个页面触发模块重新导入
- **修复建议:**
  ```python
  def _get_client() -> OpenAI:
      global _client
      current_key = os.getenv("DEEPSEEK_API_KEY", DEEPSEEK_API_KEY)
      if _client is None or _client.api_key != current_key:
          _client = OpenAI(api_key=current_key, base_url=DEEPSEEK_BASE_URL)
      return _client
  ```

#### Bug #8: `years_of_service` 与 `hire_date` 存在数据不一致

- **文件:** `data/generate_mock_data.py:52-54`
- **严重程度:** 🟢 轻微
- **代码:**

```python
yos = max(0, age-22-random.randint(0,5))
hd = datetime(2026,7,1) - timedelta(days=yos*365 + random.randint(0,180))
```

- **问题:** `years_of_service` 字段存储的是 `yos`，但 `hire_date` 是 `yos*365 + random(0,180)` 天前，导致从 `hire_date` 反推的实际工龄与 `years_of_service` 字段可能差 0~180 天
- **影响:** 如果后续代码（如基础过滤层）按 `hire_date` 重新计算工龄，会与 `years_of_service` 字段不一致
- **修复建议:**
  ```python
  # 先确定 hire_date，再反推 years_of_service
  yos_raw = max(0, age-22-random.randint(0,5))
  jitter = random.randint(0, 180)
  hd = datetime(2026,7,1) - timedelta(days=yos_raw*365 + jitter)
  # 从 hire_date 精确计算
  actual_yos = (datetime(2026,7,1) - hd).days // 365
  # 使用 actual_yos 作为 years_of_service
  ```

## 四、其他发现（非 Bug 但值得关注）

### 4.1 JSON 文件编码问题

- **文件:** `data/generate_mock_data.py:25-26`
- CSV 文件使用 `utf-8-sig`（带 BOM）→ Windows 兼容 ✅
- JSON 文件使用 `utf-8`（不带 BOM）→ Windows 默认编码 `gbk` 无法读取 ❌
- **影响:** 未来读取 `projects.json` 的代码需要显式指定 `encoding="utf-8"`，否则在 Windows 上会报 `UnicodeDecodeError`
- **建议:** JSON 文件也统一使用 `utf-8-sig` 编码，或确保所有读取 JSON 的代码都指定 `encoding="utf-8"`

### 4.2 PipelineRunner 不中断错误传播

- **文件:** `orchestrator/pipeline.py:62-67`
- 当某个 Agent 返回 `status="error"` 时，Pipeline 不停止，而是继续执行后续 Agent
- 当前设计用 `current_data = step_result.get("data", {}) or {}` 传递空数据，可能导致下游 Agent 级联失败
- **建议:** 增加一个 `stop_on_error` 参数，默认 `True`，在 Agent 失败时立即终止 Pipeline

### 4.3 360 异常评价者逻辑中，自评也会被修改

- **文件:** `data/generate_mock_data.py:119-123`
- 当被评价员工本人恰好被选入异常评价者集合时，其自评分数也会被修改
- 自评本应反映员工的自我认知，不应被异常逻辑影响
- **建议:** 在应用异常逻辑前增加 `if role != "自评"` 判断

## 五、Vibe Coding 改进建议

### 建议 1：超时/重试代码必须附带边界验证

**对应 Bug:** #1（超时失效）

**模式:** 开发者（AI）假设 `ThreadPoolExecutor` 的 timeout 能终止线程，但实际 Python 的线程模型不支持强制终止。

**规则:** 任何涉及 `timeout`、`retry`、`ThreadPoolExecutor`、`asyncio.wait_for` 的代码，要求 AI **同时生成一个边界测试**（如 `sleep(10) + timeout(2)`），**立即运行验证**，确认超时机制真正生效。

---

### 建议 2：数学公式必须附带输入输出验证表

**对应 Bug:** #2（偏差公式恒等变换）

**模式:** AI 生成了看起来"有逻辑"的代码（取绝对值、加 3、减 3），但数学上等价于不操作。这类问题在视觉 review 时极难发现。

**规则:** 要求 AI 在生成任何数学变换/公式后，**立即追加一段验证代码**，用 5-10 个典型输入值跑一遍并打印结果，确认变换效果符合预期。

---

### 建议 3：默认参数必须与规范文档交叉校验

**对应 Bug:** #3（模型名不一致）、#4（参数未使用）

**模式:** AI 生成了"合理"的默认值，但未与 `CLAUDE.md` 中的规范对齐。

**规则:** 在 prompt 中明确要求 **"所有默认参数值必须与 CLAUDE.md 中声明的技术栈一致"**，并让 AI 在生成代码后逐项自检。

---

### 建议 4：异常处理代码必须有实质差异

**对应 Bug:** #5（try/except 死代码）

**模式:** AI 倾向于生成 try/except 结构来显得健壮，但 except 块经常是复制粘贴。

**规则:** 要求 AI 在每个 except 块中**至少做一件 try 块做不了的事**（降级处理、替换策略、不同的序列化方式），否则不要写 except。如果确实无法降级，应直接让异常向上传播。

---

### 建议 5：有状态单例必须考虑运行时更新

**对应 Bug:** #6（API Key 缓存不更新）

**模式:** AI 按照"一次性初始化"的模式写了单例，但 Streamlit 的运行模型是长连接 + 用户交互式修改配置。

**规则:** 对于全局单例（client、db connection、cache），在 prompt 中明确要求 **"支持运行时通过环境变量更新配置"**，并让 AI 在初始化时每次都检查最新配置。

---

### 建议 6：数据生成脚本必须保证字段间一致性

**对应 Bug:** #8（hire_date 与 years_of_service 不一致）

**模式:** 用随机数生成多个"应该一致"的字段，但生成逻辑中引入了独立的随机 jitter。

**规则:** 要求 AI 在数据生成脚本末尾**追加一致性校验断言**（如 `assert abs(yos - calc_yos_from_hd) <= 1`），并在生成完成后自动运行。

---

### 建议 7：跨平台编码必须统一策略

**对应发现:** 4.1（JSON 编码问题）

**模式:** CSV 用了 `utf-8-sig`（良好实践），但 JSON 用了 `utf-8`（Windows 不兼容）。

**规则:** 在 prompt 中明确要求 **"所有文件 I/O 使用统一的编码策略：文本文件使用 utf-8-sig，或在读取时显式指定 encoding='utf-8'"**。

### 关键发现

代码在"正常路径"上表现良好（10 个测试全过），但**边界条件和异常路径**上存在多个 Bug。这些 Bug 的共同特征是：

> AI 生成了"看起来正确"的代码，但在逻辑上要么是恒等变换（Bug #2），要么是死代码（Bug #5），要么在运行时实际无效（Bug #1）。

这是 Vibe Coding 的典型风险——代码通过了表面验收，但隐藏着需要深度推理才能发现的逻辑缺陷。**核心对策：要求 AI 对每个关键逻辑附带自我验证代码，并在生成后立即运行。**
